# 0007. XFS instead of btrfs

Accepted, 2026-10-16. Supersedes the filesystem choice in 0002.

## Context

0002 chose btrfs for snapshots and compression. No snapshots were ever set
up; system rollback comes from NixOS generations, which don't need them.
Meanwhile the agent's heaviest writes land in the worst case for btrfs:
the Eldar VM's disk images (its home, Docker data, databases) are files that
get random overwrites, and the shared workspace is many small files.

Published benchmarks (Phoronix, Linux 6.15–7.3, 2025–2026) consistently
show btrfs's copy-on-write well behind XFS on random overwrites (4K random
writes up to ~8x; ~3.5x even with copy-on-write off) and on PostgreSQL
(~2x; ~1.45x with copy-on-write off). For small-file work there's no good
published benchmark; the closest test had btrfs and XFS about even, with
ext4 ahead.

## Decision

Root is XFS directly on LUKS: no subvolumes, `noatime`. XFS over ext4 for
reflinks (used by pnpm and `cp --reflink`) and slightly better database
results; ext4 would also have been fine.

## Consequences

VM images and databases need no special handling. We give up snapshots
(undo is NixOS generations for the system, git for the workspace, and
disposable VM disks), compression, and btrfs's data checksums; backups
become more important. XFS can't shrink, so a layout change means
reinstalling, which is scripted. Revisit if snapshots become something we
would actually use, or disk space becomes the limit.
